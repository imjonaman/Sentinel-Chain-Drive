# ===============================================================================
# 1. PROJECT PURPOSE, PROBLEM UNDERSTANDING, AND ARCHITECTURAL SCOPE
# ===============================================================================

Sentinel Chain Drive is an enterprise security and fraud intelligence platform
designed to address two systemic risks emerging in digital banking:

1. Unauthorized Autonomous AI-Agent Financial Actions:
   As financial institutions integrate autonomous and semi-autonomous AI agents
   capable of initiating payments, transfers, and account operations, agents may
   exceed authorized parameters, suffer prompt-injection or tool misuse, or
   operate under excessive standing permissions.
   Sentinel Chain Drive introduces "AgentID" and a deterministic "Policy Engine"
   to bind every AI agent to a cryptographically verifiable identity, explicit
   capability envelope, authorized beneficiary whitelist, spending limits,
   and deterministic runtime authorization checks.

2. Fragmented Cross-Institution Fund-Flow Visibility (Money Mule Networks):
   Modern financial crime leverages networks of mule accounts distributed across
   multiple independent banks to rapidly disperse illicit funds before detection.
   Because banks maintain siloed transaction records, coordinated pass-through,
   fan-out, and circular fund movements remain invisible to any single institution.
   Sentinel Chain Drive introduces "MuleChain" and an institution-aware
   "Privacy Gateway" to analyze cross-bank transaction topologies and exchange
   actionable fraud indicators without exposing raw customer accounts, personal
   data, or commercial secrets.

Architectural Scope Boundaries:
- Local Real-Time Authorization vs. Asynchronous Fraud Analysis:
  A bank's local transaction authorization decision (evaluating AgentID capabilities
  and instantaneous local limits) MUST remain on the synchronous path.
  Cross-bank graph analysis, pattern detection, and shared intelligence exchange
  MUST execute asynchronously via decoupled event pipelines to prevent ledger
  or network latency from blocking real-time payments.
- Authoritative Data Boundary:
  PostgreSQL is the single authoritative operational datastore for permissions,
  transactions, policies, cases, and audit history.
- Ledger Integration Boundary:
  DRUNIX is integrated strictly as an external append-only audit, attestation,
  and shared state coordination platform through a dedicated swappable adapter.
  Core authorization logic and fraud scoring MUST remain independent of DRUNIX.

# 2. ARCHITECTURAL BOUNDARIES AND CORE SYSTEM MODULES
# ===============================================================================

The application is decomposed into eleven modular subsystems with explicit
boundaries:

1. AgentID:
   AI-agent identity registration, cryptographic key lifecycle, capability-based
   authorization envelopes, limit tracking, and credential verification.

2. Policy Engine:
   Stateless, deterministic rule evaluation engine producing four explicit
   outcomes: ALLOW, STEP_UP, HOLD, or DECLINE, with reproducible decision traces.

3. MuleChain:
   Directed graph-based transaction intelligence engine detecting structural
   anomalies (fan-in, fan-out, rapid pass-through, and circular flows) across
   participating institutions.

4. Privacy Gateway:
   Cryptographic pseudonymization service utilizing keyed HMAC constructions to
   correlate cross-bank entity relationships without disclosing plain identifiers.

5. DRUNIX Integration:
   Pluggable ledger adapter abstracting shared intelligence publication, state
   commitments, and attestation verification behind a strict interface contract.

6. Risk Intelligence:
   Composite risk scoring engine synthesizing graph topology signals, anomaly
   indicators, freshness bounds, and provenance tracking into explainable scores.

7. Investigation and Case Management:
   Analyst workspace supporting alert triage, incident case compilation,
   evidence packaging, audit history, and simulated recovery workflows.

8. Bank Integration Gateway:
   Inbound transaction submission endpoints, core banking simulation fixtures,
   and webhooks representing institution boundary points.

9. Event Processing:
   Asynchronous messaging substrate utilizing the Transactional Outbox pattern,
   idempotent consumers, dead-letter queues, and event replay protection.

10. Web Dashboard:
    Role-aware single-page application providing operational monitoring, policy
    administration, alert investigation, and graph visualization.

11. Security and Operations:
    Role-based and attribute-based access control, automated secret management,
    system observability, hardened headers, rate limiting, and container hygiene.

# 4. CROSS-CUTTING ENGINEERING REQUIREMENTS
# ===============================================================================

Every feature across all phases MUST strictly adhere to these four pillars:

4.1 Security by Design and Least Privilege:
- Deny by Default: All API routes, policy rules, and data access points deny
  access unless explicitly permitted by verified permissions.
- Server-Side Enforcement: Client-supplied role, identity, or status headers are
  treated as untrusted input. Authentication and capability checks are executed
  exclusively on the backend.
- Secret Hygiene: Passwords, private keys, and HMAC seeds are typed as
  Pydantic `SecretStr` and NEVER emitted to logs, tracebacks, or API payloads.
- Parameterized Queries: All database interactions use SQLAlchemy ORM or
  parameterized core constructs to eliminate SQL injection vulnerabilities.
- Defensive Transport: Outbound HTTP responses carry strict security headers
  (nosniff, DENY, referrer policy, CSP). Wildcard CORS origins are forbidden.
- Information Shielding: Internal stack traces, database schemas, and connection
  strings are masked behind sanitized error codes and correlation IDs.

4.2 Privacy Engineering and Data Minimization:
- Storage Minimization: Only attributes necessary for transaction authorization
  and fraud pattern recognition are stored or processed.
- Controlled Disclosure: Institutions can only query their own transactions
  and shared cross-bank risk indicators for which they have verified authorization.
- Pseudonymization: Cross-bank account references are pseudonymized using keyed
  HMAC functions. Plain account hashes without secret keys are prohibited.
- Synthetic Test Isolation: Development and automated tests must exclusively
  use synthetic banking data. Real customer PII must never enter the codebase.

4.3 Reliability, Consistency, and Failure Handling:
- Idempotency: All payment submissions, authorization checks, and event
  consumers enforce idempotency keys to prevent duplicate side effects.
- Transactional Consistency: All persistent state transitions occur inside
  ACID database transactions.
- Transactional Outbox: Event publication to RabbitMQ is written to an outbox
  table within the same database transaction as business state changes.
- Bounded Retries: External network calls (including DRUNIX and banking gateways)
  use exponential backoff with jitter and explicit timeouts.
- Fail-Safe Authorization: If risk intelligence or external ledgers are offline,
  the system MUST fail safe according to deterministic policy rules rather than
  assuming a benign default.

4.4 Code Quality, Type Safety, and Testing Standards:
- Complete Type Annotations: All Python functions, methods, and schemas must have
  explicit type signatures compliant with strict Mypy.
- Layer Separation: Zero direct database or SQL operations inside API route
  handlers; all access flows: API -> Service -> Repository -> Database.
- Test Pyramid: Every phase must deliver isolated unit tests, integration tests
  with real/mock databases, and adversarial negative tests.
- Reproducible Migrations: Schema updates must include forward (`upgrade`) and
  reversal (`downgrade`) scripts tested against PostgreSQL.

Feature 3.2: Cryptographic Capability Credentials
- Actor: Autonomous AI Agent / Authorizing Service.
- Purpose: Cryptographically sign proposed transaction intents using agent private keys.
- Credential Model:
  - Claims: `agent_id`, `nonce`, `timestamp`, `expires_at`, `action_type`,
    `transaction_hash` (SHA-256 over amount, currency, origin, destination).
  - Signature: Ed25519 signature over canonical JSON representation of claims.
- Cryptographic Engine (`src/sentinel_chain_drive/core/crypto.py`):
  - Signature verification using PyCA `cryptography.hazmat.primitives.asymmetric.ed25519`.
  - Nonce cache & replay protection: Reject any request with a timestamp older than
    300 seconds or a nonce already processed within the validity window.
  - Key rotation support: Query active public key by `agent_id` and `key_version`.

Feature 3.3: Capability-Based Authorization Envelopes
- Actor: Security Administrator / Policy Designer.
- Purpose: Define strict operational envelopes restricting agent capabilities.
- Data Model (`src/sentinel_chain_drive/db/models/capability.py`):
  - `id`: UUID (Primary Key).
  - `agent_id`: UUID, ForeignKey("agents.id"), Indexed.
  - `max_single_transaction_amount`: Numeric(18, 4), Not Null.
  - `max_daily_cumulative_amount`: Numeric(18, 4), Not Null.
  - `allowed_currencies`: JSON (List[str], e.g., ["USD"]).
  - `allowed_purpose_codes`: JSON (List[str], e.g., ["VENDOR_PAYMENT"]).
  - `allowed_destination_accounts`: JSON (Optional whitelist of approved account IDs).
  - `operating_window_start_utc`: Time, Nullable.
  - `operating_window_end_utc`: Time, Nullable.
  - `is_active`: Boolean, Default True.
  - Standard `TimestampMixin`.

Feature 3.4: Agent Action Authorization Service
- Actor: Transaction Ingestion Gateway.
- Purpose: Synchronously verify agent credential, signature, and capability match.
- Service: `AgentAuthorizationService` (`src/sentinel_chain_drive/services/agent_service.py`).
- Evaluation Steps:
  1. Retrieve agent by `agent_id`. Verify status == "ACTIVE".
  2. Verify Ed25519 signature against registered agent `public_key`.
  3. Verify nonce uniqueness and check timestamp skew (|now - ts| <= 300s).
  4. Fetch active capability envelope.
  5. Check `transaction.amount <= max_single_transaction_amount`.
  6. Calculate cumulative spending in the current 24-hour window:
     Query sum of settled/authorized transactions for agent within past 24h.
     Verify `(cumulative + current_amount) <= max_daily_cumulative_amount`.
  7. Verify `currency` in `allowed_currencies`.
  8. Verify `purpose_code` in `allowed_purpose_codes`.
  9. If destination whitelist is configured, verify destination account is present.
  10. Record immutable `authorization_records` entry with decision, reason, and signature hash.
- Output: `AuthorizationResult(is_authorized=bool, reason_code=str, details=dict)`.

3.2 Dependencies:
- Requires Phase 1 core security and Phase 2 banking models (`accounts`, `transactions`).

3.3 Required Tests:
- Cryptographic verification tests: Valid signature accepted, tampered payload rejected,
  mismatched public key rejected.
- Replay tests: Duplicate nonce within time window rejected.
- Clock skew tests: Timestamp older than 300s rejected.
- Capability tests: Exceeded single limit rejected, cumulative daily limit breach rejected,
  disallowed currency rejected, out-of-window transaction rejected.
- Inactive/Revoked agent tests: Revoked agent cannot authorize any action.

3.4 Exit Gate & Acceptance Criteria:
- No transaction can be authorized under an agent identity without a cryptographically
  valid signature.
- An agent cannot execute an action exceeding its assigned single or daily capability limits.
- Full negative test coverage for tampering, replay, and expiration.

# PHASE 4: DETERMINISTIC POLICY ENGINE
# -------------------------------------------------------------------------------
Objective:
Implement a deterministic, explainable rule evaluation engine combining agent
capabilities, transaction context, account status, and institution rules into
authoritative ALLOW, STEP_UP, HOLD, or DECLINE decisions.

4.1 Feature Breakdown:

Feature 4.1: Policy Specification and Rule Model
- Purpose: Provide modular, versioned policy rules evaluated without side effects.
- Decision Outcomes:
  - `ALLOW`: Request meets all criteria; transaction may proceed to settlement.
  - `STEP_UP`: Human supervisor or multi-party approval required before execution.
  - `HOLD`: Potential risk detected; transaction placed in institutional review queue.
  - `DECLINE`: Request violates hard security, limit, or regulatory boundaries.
- Data Model (`src/sentinel_chain_drive/db/models/policy.py`):
  - `id`: UUID (Primary Key).
  - `institution_id`: UUID, ForeignKey("institutions.id"), Nullable (Null = Global).
  - `policy_code`: String(64), Indexed.
  - `version`: Integer, Not Null.
  - `priority`: Integer, Not Null (Lower number = higher precedence).
  - `rules`: JSON (DSL representing conditional predicates).
  - `is_active`: Boolean, Default True.
  - Standard `TimestampMixin`.

Feature 4.2: Policy Evaluation Engine
- Component: `PolicyEngine` (`src/sentinel_chain_drive/services/policy_engine.py`).
- Inputs:
  - Transaction context (amount, currency, origin, destination, purpose).
  - AgentID authorization result (from Phase 3).
  - Account flags and status (from Phase 2).
  - Historical velocity (transactions count, aggregate amount in time window).
  - Available risk indicators (from Phase 5/6, if present).
- Precedence & Conflict Resolution:
  1. Security Violations: If AgentID signature fails or agent revoked -> Immediate DECLINE.
  2. Account Restrictions: If origin/dest account FROZEN -> Immediate DECLINE.
  3. Hard Limits: If transaction exceeds absolute institutional cap -> Immediate DECLINE.
  4. Step-Up Triggers: If transaction amount exceeds threshold requiring dual control,
     or risk score in medium band -> Return STEP_UP.
  5. Hold Triggers: If suspicious rapid velocity detected -> Return HOLD.
  6. Default Rule: If all checks pass -> Return ALLOW.
  7. Fail-Safe Boundary: If policy evaluation errors or unexpected exceptions occur,
     engine MUST default to DECLINE/HOLD, never ALLOW.
- Decision Trace:
  Returns `PolicyDecision`:
  - `decision`: Enum ("ALLOW", "STEP_UP", "HOLD", "DECLINE").
  - `reason_codes`: List[str] (e.g., ["AGENT_AUTH_OK", "DUAL_APPROVAL_REQUIRED"]).
  - `policy_id`: UUID.
  - `policy_version`: Integer.
  - `evaluated_at`: DateTime(UTC).
  - `correlation_id`: String.

Feature 4.3: Step-Up and Approval Workflow
- Actor: Institutional Compliance Supervisor.
- Purpose: Manage the lifecycle of transactions requiring step-up approval.

# PHASE 5: MULECHAIN - GRAPH-BASED FRAUD INTELLIGENCE
# -------------------------------------------------------------------------------
Objective:
Construct a directed transaction graph engine detecting money mule behavioral
patterns across participating institutions without blocking the real-time payment path.

5.1 Feature Breakdown:

Feature 5.1: Graph Model and Construction
- Engine: NetworkX directed multigraph (`MultiDiGraph`).
- Node Schema:
  - `AccountNode`: `account_id`, `institution_id`, `account_type`, `created_at`.
  - `InstitutionNode`: `institution_id`, `institution_code`.
- Edge Schema:
  - `TransactionEdge`: `transaction_id`, `amount`, `currency`, `timestamp`,
    `purpose_code`, `status`.
- Time-Window Bounded Subgraphs:
  Support sliding inspection windows (e.g., past 1 hour, 24 hours, 7 days, 30 days)
  to prevent unbounded memory consumption.

Feature 5.2: Topological Fraud Detection Rules
Module: `src/sentinel_chain_drive/services/mulechain/detectors.py`.
- Rule 1: Fan-In Detection (Smurfing Ingress)
  - Pattern: Multiple distinct source accounts (>= N, default 5) transferring funds
    to a common destination account within time window W (default 24h), where
    individual amounts are below reporting thresholds.
  - Output: `FanInIndicator(dest_account_id, source_count, aggregate_amount, time_window)`.
- Rule 2: Fan-Out Detection (Rapid Dispersal)
  - Pattern: A single source account distributing funds to multiple distinct destination
    accounts (>= N, default 5) across different institutions within window W.
  - Output: `FanOutIndicator(source_account_id, dest_count, aggregate_amount, time_window)`.
- Rule 3: Rapid Pass-Through Detection (Transit Mule)
  - Pattern: Account A receives funds from Account S, and within delta T (default <= 30 mins),
    Account A transfers >= 85% of received funds to Account D.
  - Output: `PassThroughIndicator(mule_account_id, ingress_tx, egress_tx, retention_ratio)`.
- Rule 4: Circular Fund-Flow Detection (Layering)
  - Pattern: Directed cycles in transaction graph (A -> B -> C -> A) within window W.
  - Output: `CircularFlowIndicator(cycle_path, total_cycled_amount)`.

Feature 5.3: Explainable Risk Scoring Engine
- Component: `RiskScoringService` (`src/sentinel_chain_drive/services/mulechain/scoring.py`).
- Score Range: 0 to 100 (Integer):
  - 0-29: LOW_RISK.
  - 30-59: MEDIUM_RISK.
  - 60-84: HIGH_RISK.
  - 85-100: CRITICAL_RISK.
- Scoring Formulation:
  - Deterministic weighted combination of active indicators + velocity modifiers.
  - Evidence preservation: Every computed score links directly to the underlying
    indicators, triggering transaction IDs, and rule versions.

Feature 5.4: Asynchronous Processing and Alert Generation
- Service: `MuleChainProcessor`.
- Data Model (`src/sentinel_chain_drive/db/models/alert.py`):
  - `id`: UUID (Primary Key).
  - `alert_code`: String(64), Indexed (e.g., "MULE_RAPID_PASSTHROUGH").
  - `severity`: Enum ("LOW", "MEDIUM", "HIGH", "CRITICAL").
  - `status`: Enum ("NEW", "INVESTIGATING", "RESOLVED", "FALSE_POSITIVE").
  - `primary_account_id`: UUID, ForeignKey("accounts.id"), Indexed.
  - `primary_institution_id`: UUID, ForeignKey("institutions.id"), Indexed.
  - `risk_score`: Integer, Not Null.
  - `evidence_data`: JSON (Structured indicator parameters and transaction IDs).
  - `detection_rule_version`: String(16), Not Null.
  - Standard `TimestampMixin`.

5.2 Dependencies:
- Requires Phase 2 transaction domain. Operates asynchronously from Phase 4 authorization.

5.3 Required Tests:

Feature 6.3: Privacy Gateway Access Control & Tenant Isolation

- Authorization Rules:

# PHASE 8: EVENT PROCESSING AND SYSTEM COORDINATION
# -------------------------------------------------------------------------------
Objective:

8.1 Feature Breakdown:

Feature 8.1: Transactional Outbox Pattern
- Purpose: Guarantee at-least-once event publication without dual-write inconsistencies.
- Data Model (`src/sentinel_chain_drive/db/models/outbox.py`):
  - `id`: UUID (Primary Key).
  - `event_type`: String(64), Indexed (e.g., "TRANSACTION_AUTHORIZED").
  - `aggregate_type`: String(32), Indexed ("TRANSACTION", "AGENT", "ALERT").
  - `aggregate_id`: UUID, Indexed.
  - `payload`: JSON, Not Null.
  - `correlation_id`: String(64), Indexed.
  - `status`: Enum ("PENDING", "PUBLISHED", "FAILED").
  - `retry_count`: Integer, Default 0.
  - Standard `TimestampMixin`.
- Outbox Relayer: Background worker that polls pending outbox entries, publishes
  to RabbitMQ, and marks them `PUBLISHED` upon broker acknowledgment.

Feature 8.2: RabbitMQ Topology and Event Schemas
- Exchange Architecture:
  - `sentinel.events` (Topic Exchange).
  - Routing Keys: `transaction.submitted`, `transaction.authorized`, `transaction.held`,
    `mulechain.alert_raised`, `privacy.indicator_shared`.
- Queue Architecture:
  - `q.mulechain.transactions` (Consumes transaction events for graph analytics).
  - `q.drunix.submissions` (Consumes commitments for ledger recording).
  - `q.investigations.alerts` (Consumes alerts for case triage).
- Dead-Letter Handling:
  - Every queue configured with `x-dead-letter-exchange: sentinel.dlx`.
  - Max retry count: 5 with exponential backoff before routing to dead-letter queue.

Feature 8.3: Idempotent Event Consumers
- Consumer Contract:
  - Every message carries a unique `event_id` and `correlation_id`.
  - Consumer tracks processed IDs in `processed_events` table within local transaction.
  - Duplicate messages are acknowledged and discarded without re-execution.

8.2 Dependencies:
- Requires Phases 2, 3, 4, 5, 6, and 7. Introduces RabbitMQ broker.

8.3 Required Tests:
- Outbox consistency: Database rollback rolls back the outbox event.
- Idempotency tests: Replaying identical event payloads produces no duplicate state changes.
- Dead-letter tests: Poison messages reaching max retry count move cleanly to DLQ.
- End-to-end tracing: Single transaction lifecycle traceable via correlation ID across queues.

8.4 Exit Gate & Acceptance Criteria:
- No events lost during simulated broker restarts.
- End-to-end workflow verified from transaction submission -> outbox -> RabbitMQ -> graph update.
